A practical reference for the Colibri + Qwen3-Coder + Continue project: model architecture, caches, hardware, request lifecycle, observability, and a controlled optimization program.

Hardware and timing figures are historical observations from this project, not a live server status or a performance guarantee.

What this project does

Colibri serves a local language model through an API. Continue connects from the editor and orchestrates coding tasks: assembling context, requesting answers, executing approved tools, and sending tool results back. The Inference Observatory makes server activity visible.

What the model computes

Tokens and embeddings

A token is a piece of text, such as a word fragment, punctuation, or part of code. Tokenization turns text into IDs; embeddings turn IDs into numerical vectors. Character counts are useful for inspecting requests but cannot replace actual token counts.

48 layers: successive transformations

Each transformer layer applies attention and a feed-forward transformation, along with normalization and residual connections. All 48 layers participate in processing this model’s tokens. Layer count is fixed by the architecture; changing RAM or prompt length does not change it. Layers are not reliably assignable to simple jobs such as “grammar” or “reasoning.”

Mixture of Experts: many choices, a few activated

Each layer’s MoE feed-forward part has 128 learned expert networks. A router selects eight for each token and combines their outputs. Different layers and tokens can select different expert IDs. Attention and other shared computation still run. Experts are learned numerical networks, not separately named specialists or independent chatbots.

30B versus A3B

30B describes approximately 30 billion total parameters; A3B indicates approximately three billion active parameters per token. Activation is sparse, but storing the entire checkpoint still requires capacity for the total model. Dense models use their feed-forward parameters on every token; MoE introduces routing and caching opportunities as well as complexity.

For 2,500 input tokens: 2,500 × 48 = 120,000 token-layer evaluations, and 2,500 × 48 × 8 = 960,000 expert selections. These are conceptual counts, not FLOPs, independent disk reads, or distinct experts. Computation can be batched, and weights can be reused.

KV remembers previously computed conversation information. Expert caching keeps model components nearby. File caching retains file data. A warm expert cache does not imply a reusable KV prefix, and a request to read a file need not reach physical SSD storage.

What are the “Keys” and “Values”?

Attention creates a Query for the current position. It compares that Query against earlier Keys to determine relevance, then combines the corresponding Values. Cached K/V avoid recomputing the earlier representations, but a new token still performs attention over its available context. Longer context can therefore slow decode even with a valid KV cache.

Within one response versus across requests

During a response, the engine reuses prompt K/V as it generates tokens. Across requests, the engine must also recognize a compatible token prefix and retain the right sequence state. Identical-looking text may tokenize differently after chat-template or tool-call formatting changes. Changed system prompts, tool ordering, history trimming, and other requests sharing a slot can defeat reuse.

Source-verified correction: the engine already implements prefix reuse. COLI_KV_PREFIX=0 disables it; COLI_PREFIX_LOG=1 logs reuse decisions. The inspected path requires a compatible retained prefix, rather than assuming arbitrary partial-prefix reuse. Diagnose actual reuse before proposing to “enable KV caching.”

A useful approximate KV-memory formula is 2 × layers × cached tokens × KV heads × head dimension × bytes per element. The factor two is for K and V; allocation overhead, precision, implementation layout and multiple slots also matter. More concurrent slots can multiply memory needs.

From clicking Send to completing a task

Build context→Network & gateway→Queue→Prefill→Decode→Tool execution ↺
  • Prefill: processes input token positions not reused from a compatible cache. Includes attention and expert computation and may require weight reads.
  • Decode: generates output autoregressively. Each new token depends on the preceding sequence; speculative techniques can sometimes amortize work.
  • TTFT: time to first token/output. May include queueing, prompt preparation, prefill and first-token work, depending on the measurement boundary.
  • Tool time: file reads, searches, commands or edits outside the model. Each tool round can add another prefill and decode.

Fitting a model is different from running it efficiently

RAM must support dense/shared weights, expert tensors, KV state, temporary computation buffers, the gateway, and other applications. Process RSS includes more than model weights. Checkpoint bytes on disk cannot be subtracted from RSS to obtain “weights still on disk.” The complete checkpoint remains on disk even when cached copies exist.

CPU and memory bandwidth

Matrix computation consumes CPU execution capacity, but moving weights from RAM also consumes bandwidth. More threads can stop helping once memory bandwidth or synchronization becomes the limit. This CPU has six physical cores and 12 hardware threads; benchmark several thread counts rather than treating 12 as automatically optimal.

NVMe, page cache and swap

NVMe reduces cold-loading latency but remains much slower than RAM for repeatedly accessed tensors. File-cache hits may mask physical I/O. Conversely, swapping model pages out under memory pressure can erase cache gains. Measure swap-in/out rates, major page faults and storage reads during the request, not just “free memory.”

GPU offloading

The available GT 1030 has a limited memory budget. A compatible backend might accelerate a subset of work, but transfers, kernel support, precision, build compatibility and CPU/GPU balance determine the benefit. GPU presence alone does not imply use or speedup. Benchmark supported CUDA/Vulkan paths and retain the CPU baseline.

Quantization and quality

Quantization reduces the bits used to represent weights. It can reduce storage, memory traffic and cache pressure, but performance depends on the actual kernels and conversion overhead. Lower precision can affect coding accuracy and tool-call reliability, so evaluate quality alongside speed. KV precision is a separate setting from expert-weight precision.

Thermals, clock speeds and power

Sustained heat or power limits can reduce CPU frequency during long prefill runs. Collect temperature and frequency along with performance. Changing a power policy affects the whole workstation and should be a controlled experiment.

Reducing the output ceiling prevents unnecessarily long answers and may affect memory reservation. It does not automatically shorten an unchanged prompt’s prefill. Increasing concurrent slots can improve aggregate throughput, but it consumes additional memory and can worsen latency for one user.

Use total task completion time and correctness as the final acceptance criteria. A faster decode rate is valuable only in proportion to the share of time spent decoding.

Make every improvement reproducible

  1. Record model/checkpoint, engine revision/build, cache cap, context limit, threads, backend and background memory usage.
  2. Use fixed representative requests: tiny chat, coding prompt with tools, repeated-prefix follow-up, changed-prefix request, and long tool result.
  3. Separate cold process startup, warm expert-cache state and warm KV-prefix state. They are different experimental conditions.
  4. Capture queue time, prompt/reused tokens, prefill time, first-output time, decode tokens/s, request wall time and complete agent task time.
  5. Record process RSS, available memory, swap activity, physical read bytes, expert hits/misses, CPU utilization/frequency and temperature.
  6. Repeat each condition several times; report median and range. Change one parameter at a time and retain a rollback configuration.
  7. Validate resulting code, tool-call structure and task success. Reject speed gains that break the workflow.

Access, persistence and operational limits

  • Localhost: 127.0.0.1 means the device opening the browser. Other devices use the server’s LAN address.
  • Authentication: the dashboard needs the configured key. The UI keeps it in browser session storage for the tab; the key is not included in this document.
  • Prompt capture: COLI_ACTIVITY_CONTENT=1 enables previews for new requests. They may contain confidential code; keep access controlled. Plain HTTP on a LAN does not encrypt credentials or prompts.
  • Restart: resets in-memory request history and computation/cache state; the model files remain on disk.
  • Queueing: a second request can wait behind a long prefill. Repeated retries can compound congestion. Cancellation must propagate to the engine.
  • Availability: a manually launched process is not equivalent to a managed service. Auto-start, restart policy, log rotation and health monitoring are separate production tasks.
  • Dashboard overhead: current polling uses existing snapshots. It still consumes some CPU/network/logging resources; benchmark enabled versus disabled before claiming zero overhead.

Terms to recognize

Parameters / weights

Learned numbers defining the model’s transformations; they are not conversation memory.

Context window

The sequence budget available to a request. Input and output compete for this limit in the current engine.

RSS

Resident Set Size: process pages currently resident in RAM. Includes weights and other allocations.

LRU / eviction

Least Recently Used is a common policy for replacing cached entries. Actual implementation may protect pinned or busy entries.

Bandwidth versus latency

Bandwidth is data per second; latency is time to complete an operation. Both can limit weight access.

Batching

Computing multiple rows or requests together for better hardware utilization. Throughput improvements can trade off against memory or single-request latency.

Speculative decoding

Proposing multiple tokens then verifying them. Only beneficial when accepted tokens save more work than proposal and verification cost.

Temperature / sampling

Controls how token probabilities are sampled. It changes output behavior, not the model’s layer count or stored weights.

Tool schema

A description of a tool’s name, arguments and use. Definitions add input tokens even when the model never calls the tool.

Throughput / latency

Throughput measures work per second. Latency measures one request’s wait. Improving one does not always improve the other.
